# New API 企业官网改版实施计划

> 文档用途：本文件用于直接交给 AI 编程智能体，作为企业官网改版的产品、内容、页面和实现提示词。
>
> 改版范围：仅公共官网与公共认证页面，不修改后台管理页面、不修改后端接口、不调整计费或渠道业务逻辑。
>
> 核心定位：面向中小企业的 AI 模型接入与治理平台。

---

## 1. 项目目标

将当前偏开发者工具、模型价格站和管理控制台风格的公共网站，改造成一个具备企业可信度、产品表达能力和销售转化能力的 B2B 企业官网。

改版完成后，访问者应能在较短时间内明确理解：

1. 平台为谁服务：需要在产品或业务中接入 AI 能力的中小企业、SaaS 公司和开发团队。
2. 平台解决什么问题：多模型接入复杂、供应商分散、密钥难管理、服务稳定性不足、用量成本不透明。
3. 平台提供什么价值：统一 API、模型路由、企业权限、用量成本、调用日志和集中治理。
4. 下一步如何行动：免费开始接入、查看开发文档、登录控制台或联系企业服务。

### 1.1 核心品牌主张

主标题建议：

> 让企业更快、更稳定地接入 AI 能力

副标题建议：

> 通过一套接口连接主流 AI 模型，统一管理模型路由、调用权限、用量成本和运行日志，降低企业 AI 应用的集成与运维复杂度。

四个核心价值关键词：

- 接得快：统一接口，减少重复开发。
- 用得稳：多渠道调度和故障切换，降低单一供应商影响。
- 管得住：集中管理用户、密钥、模型权限、额度和调用策略。
- 看得清：统一查看调用量、Token、费用、错误和运行状态。

### 1.2 目标客户

主要客户：

- 希望为现有产品增加 AI 功能的 SaaS 公司。
- 正在建设智能客服、知识助手、内容生成或办公自动化系统的中小企业。
- 需要同时接入多家模型供应商的 AI 创业团队。
- 需要统一管理模型密钥、调用额度和费用的企业研发团队。
- 为客户交付 AI 应用的软件服务商和系统集成商。

主要访问角色：

- 企业负责人：关心业务价值、实施周期、服务可靠性和总体成本。
- 技术负责人：关心架构兼容性、稳定性、安全、可观测性和迁移成本。
- 产品经理：关心业务场景、模型能力、迭代效率和使用体验。
- 开发人员：关心接口规范、代码示例、模型列表、错误处理和快速接入。

## 2. 改版边界

### 2.1 本次包含

- 公共官网整体信息架构。
- 公共 Header、Mega Menu、移动端导航和 Footer。
- 首页、产品、解决方案、行业、客户案例、安全、价格、关于和联系页面。
- 现有模型价格页面的企业化改造。
- 登录、注册、找回密码、OTP 和 OAuth 等公共认证页面的视觉统一。
- 404、500、503 等公共错误页面的视觉统一。
- 每个公共页面的 SEO 元信息和分享信息规划。
- 全部新增文案的国际化。
- PC、平板和移动端响应式设计。
- 无障碍、性能和安全要求。

### 2.2 本次不包含

- 不修改 Dashboard、Channels、Models、Users、System Settings 等后台页面。
- 不修改后台导航和后台布局。
- 不修改后端接口、数据库或认证机制。
- 不修改模型路由、计费、渠道、配额和日志业务逻辑。
- 不创建虚假的客户案例、客户 Logo、认证资质、SLA 或经营数据。
- 不新增在线咨询、CRM、表单提交等后端服务。
- 没有现成接口时，不实现伪造成功的联系表单。
- 不在未确认前新增 npm、Bun 或其他第三方依赖。

### 2.3 实施原则

- 官网与控制台分工明确：官网负责解释价值和获取客户，控制台负责产品使用。
- 优先复用现有设计系统、Base UI、Tailwind CSS、图标和公共工具。
- 新页面按稳定业务概念拆分，不创建数千行的大型页面组件。
- 所有事实性宣传必须能够由现有产品功能、文档或公司材料证明。
- 暂时无法证明的能力使用中性表达或直接不展示。
- 不使用“全网最低”“银行级安全”“无限稳定”等不可验证或绝对化表述。

### 5.3 客户痛点区

标题：

> 接入多个 AI 模型，不应该意味着维护多套系统

左侧“企业常见问题”：

- 每家模型供应商的接口和鉴权方式不同。
- 密钥分散在不同项目、服务器和个人账号中。
- 单一模型或渠道故障会直接影响业务。
- 用量和费用分散，难以统一核算。
- 无法按用户、项目或部门控制额度。
- 失败请求需要登录多个平台排查。

右侧“平台带来的改变”：

- 使用统一接口调用多个模型。
- 集中管理供应商密钥和企业 API Key。
- 根据策略分配请求并设置备用渠道。
- 统一查看调用量、Token、费用和错误。
- 按用户、项目和业务设置权限与额度。
- 使用统一日志定位问题。

### 5.4 四大价值区

采用四个大型能力卡片，不使用密集小卡片。

#### 接得快

- 标题：一套接口，减少重复开发。
- 内容：使用统一 API 规范连接多个模型供应商，降低模型切换和业务迁移成本。
- 视觉：代码示例与模型切换控件。

#### 用得稳

- 标题：让单一渠道故障不再直接影响业务。
- 内容：根据渠道状态和业务策略分配请求，在异常时使用可用服务。
- 视觉：主渠道、备用渠道和健康状态流程。
- 注意：只展示当前产品真实支持的路由能力。

#### 管得住

- 标题：统一管理企业 AI 使用权限。
- 内容：集中管理用户、API Key、模型权限、调用额度和使用范围。
- 视觉：用户、密钥、角色和额度关系图。

#### 看得清

- 标题：每一次模型调用都有清晰记录。
- 内容：按用户、项目、模型和时间查看调用量、费用和异常。
- 视觉：用量趋势、费用占比和错误日志。

### 5.5 产品工作流程

标题：

> 从模型接入到企业治理，只需一个平台

流程：

1. 接入模型供应商或现有渠道。
2. 创建企业 API Key。
3. 为项目配置模型和额度。
4. 业务系统通过统一 API 发起调用。
5. 平台记录用量、费用和运行日志。

每一步需要：

- 对应界面或图标。
- 连接关系清晰。

## 6. 产品能力页面

路由：/product

页面目标：系统介绍平台核心能力，供技术负责人和产品负责人进行产品评估。

SEO 标题建议：

> 企业 AI 模型接入平台 - 产品能力 | 品牌名

### 6.1 产品页 Hero

- H1：企业 AI 模型接入与治理能力，集中在一个平台。
- 副标题：连接模型、管理密钥、控制权限、追踪用量并提升服务稳定性。
- CTA：免费开始接入、查看开发文档。

### 6.2 产品架构

四层架构：

1. 业务应用层：客服、知识库、SaaS、内容工具、内部系统。
2. 统一接入层：兼容接口、认证、请求转换。
3. 治理层：路由、限流、权限、额度、日志、费用。
4. 模型供应层：公有模型、云厂商模型、兼容模型、自有模型。

架构图必须适配移动端，移动端改为纵向流程。

### 6.3 核心能力模块

#### 统一模型 API

- 多供应商统一调用。
- 减少不同接口之间的适配代码。
- 支持模型切换。
- 提供开发文档和示例。

#### 模型路由与稳定性

- 渠道优先级。
- 可用性状态。
- 失败处理。

## 18. 统一视觉规范

### 18.1 设计方向

关键词：

- 专业
- 稳定
- 清晰
- 开放
- 企业可信
- 现代技术感

避免：

- 大面积紫色霓虹。
- 过度玻璃拟态。
- 满屏发光球体。
- 通用机器人或 AI 大脑素材。
- 所有文字都使用渐变色。
- 大量无意义循环动画。
- 过密的功能卡片。

### 18.2 推荐色彩

可在不破坏现有主题能力的前提下调整：

- 深色品牌色：#0B1F3A。
- 主交互蓝：#2563EB。
- 辅助青色：#14B8A6。
- 主背景：#FFFFFF。
- 辅助背景：#F6F8FB。
- 深色展示区：#071426。
- 默认边框：#E5EAF0。

所有颜色最终应映射到现有 CSS 变量和设计 Token，不在组件中大面积硬编码。

### 18.3 排版

- 页面最大内容宽度：1200 至 1280 像素。
- 正文最大阅读宽度：680 至 760 像素。
- H1：桌面端 48 至 64 像素，移动端 36 至 44 像素。
- H2：桌面端 36 至 44 像素，移动端 28 至 34 像素。
- 正文：16 至 18 像素。
- 大区块上下间距：桌面端 96 至 128 像素，移动端 64 至 80 像素。
- 卡片圆角：12 至 16 像素。
- 正文行高保持 1.6 左右。

### 18.4 图片和产品视觉

优先级：

1. 真实产品界面。
2. 经过脱敏的产品截图。
3. 使用 HTML、CSS 或 SVG 绘制的架构图。
4. 与具体业务场景有关的插图。

禁止：

- 截图中出现真实 API Key。
- 截图中出现真实用户邮箱和企业数据。
- 使用未经授权的客户 Logo。
- 使用与产品无关的通用 AI 素材作为主要视觉。

### 18.5 动效

允许：

- 请求流向动画。
- 模型节点状态变化。
- 页面区块轻量进入动画。
- Tab 切换和数据图表过渡。

要求：

- 支持 prefers-reduced-motion。
- 移动端减少复杂动画。
- 不使用会阻塞主线程的大型 Canvas 动画。
- 不因动效引入新的大型依赖。

## 20. 国际化要求

所有新增用户可见文案必须支持：

- en
- zh
- zh-TW
- fr
- ja
- ru
- vi

要求：

- React 组件使用 useTranslation。
- 使用英文源文本作为平铺 JSON Key，遵循项目现有规范。
- 禁止在 JSX 中硬编码中文或英文用户文案。
- 完成后从 web 目录执行 bun run i18n:sync。
- 检查七种语言没有缺失键、额外键和未翻译项。
- 切换语言时同步更新 document.documentElement.lang。
- 继续同步 document.documentElement.dir。
- 页面标题和 SEO 描述也要随语言切换。

## 21. SEO 和分享规范

每个公共页面必须定义：

- 唯一 title。
- 唯一 meta description。
- canonical 地址。
- Open Graph title。
- Open Graph description。
- Open Graph image。
- Twitter Card 信息。
- robots 规则。

SEO 规则：

- H1 每页只有一个。
- 页面标题与 H1 不完全重复，但语义一致。
- 标题层级连续，不从 H1 直接跳到 H4。
- 解决方案和行业页面使用独立文案，避免重复页面。
- 登录、注册、OAuth、Setup 和错误页设置 noindex。
- 如果当前纯 SPA 无法完整支持服务端元信息，至少保证客户端路由切换时正确更新 document title 和 meta。
- 不为了 SEO 堆砌“AI 接口”“大模型 API”等关键词。

建议主要关键词方向：

- 企业 AI 接入
- AI 模型 API
- 多模型统一接口
- AI 模型网关
- 企业模型管理
- AI 成本管理
- SaaS AI 接入

## 22. 无障碍要求

- 使用 header、nav、main、section、footer 等语义结构。
- 所有图片提供准确 alt，装饰图片使用空 alt。
- 所有按钮和链接拥有可理解名称。
- Mega Menu、Tabs、Accordion、Dialog 和移动导航支持键盘操作。
- 焦点样式清晰可见。
- 颜色对比度满足 WCAG AA 基本要求。
- 表单错误与字段建立关联。
- 不只依赖颜色表达成功、错误或渠道状态。
- 动画支持 reduced motion。
- 切换语言时正确更新 html lang。

## 23. 性能要求

- 公共官网路由继续使用路由级拆包。
- 大型产品截图和案例图片使用懒加载。
- 首屏主视觉需要明确尺寸，避免布局偏移。
- 图片使用合适格式和响应式尺寸。
- 不将 VChart、后台表格和管理模块打入官网首屏包。
- 官网不需要图表时不要加载图表库。
- 不使用大型背景视频作为默认首屏。
- 图标优先使用现有图标库或轻量 SVG。
- 避免在渲染路径中重复读取大型 localStorage 数据。
- 不新增全局状态来保存静态营销文案。
- 生产构建后检查路由 Chunk，确保后台与官网代码没有被错误合并。

建议目标：

- 首屏无明显布局跳动。
- 移动端弱网下仍能先展示标题、说明和 CTA。
- 主导航无需等待大型动态组件加载。

## 24. 安全要求

- 禁止直接渲染未消毒的后台 HTML 配置。
- 自定义 HTML 必须复用统一的 HtmlContent 或 DOMPurify 策略。
- 禁止通过 new Function、eval 或字符串脚本执行营销配置。
- 外部链接使用正确的 rel 属性。
- iframe 必须配置 sandbox、referrerPolicy 和明确来源。
- postMessage 在已知目标来源时不得使用通配符。
- 联系方式、文档地址和控制台地址从现有安全配置读取。
- 禁止在代码、截图、Markdown 或页面文案中写入密钥和 Token。
- 不展示内部接口错误、堆栈和服务器信息。

## 25. 内容真实性规则

AI 智能体实现时必须遵循：

1. 不虚构客户名称和客户 Logo。
2. 不虚构成功率、节省比例和接入时间。
3. 不虚构模型数量，必须从现有配置或产品材料确认。
4. 不虚构 SLA、私有化部署和专属实例能力。
5. 不虚构 SOC 2、ISO 27001、等保等认证。
6. 不使用“永久免费”“绝对安全”“永不故障”等绝对化承诺。
7. 不将开源项目本身的能力直接描述为运营服务已经提供的能力。
8. 不清楚的数据以配置项、占位说明或条件渲染处理，不能直接写死并上线。
9. 所有价格、模型和计费单位必须来自当前系统真实数据。
10. 示例数据必须明确标注为演示数据。
